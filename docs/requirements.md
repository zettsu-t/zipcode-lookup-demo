# 結婚式の返礼はがきを送るWebサービス

## 1. 背景と目的

### サービスの範囲

結婚式の出席者に対して、返礼はがきを一斉送信するウェブサービスを立ち上げる。

返礼はがきに記載する内容は以下の通りである。これらをウェブサービスに登録すると、はがきが出席者に対して送られる。少なくとも以下を登録する必要がある。

- 結婚した人(差出人) : 差出人の住所と名前(連名)
- 宛先 : 出席者の住所と名前(連名かもしれない)

実用的なサービスとしては以下が必要であるが、それは後で追加するものとして、今は考慮しない。

- はがきに印刷する画像をアップロードする
- はがきに印刷する画像をプレビューしながら編集する
- 課金、ログイン認証など

### 住所

- 差出人の自宅住所、郵便番号、名前(連名)を登録する
- 出席者の送付先住所、郵便番号、名前(連名かもしれない)を登録する

### 郵便番号

1. 差出人は自宅の住所も郵便番号も覚えている。よって郵便番号を入力すると住所を補完すると便利である
2. 結婚式の出席者は、送付先住所は教えてくれるかもしれないが、郵便番号は記入しないかもしれない。よって住所を入力すると郵便番号の候補を補完すると便利である

段階的に開発する。1だけ実装したものをstage 1、1と2の両方を実装したものをstage 2と呼ぶ。

---

## 2. 機能要件 (FR : Functional Requirements)

### Stage 1

#### FR-1-1: 差出人の住所登録

- 1アプリにつき1レコードに限る(結婚した人とその自宅)
- 差出人の氏名を連名で記入できる。記入方法は自由記述とする。
- 名前の表記を解析しない(氏名表記は文化によって大きく異なるので)

#### FR-1-2: 出席者リスト管理

- 1アプリにつき0レコード以上複数とする
- 出席者の名前を記入できる。記入方法は自由記述とする。
  - 名前の表記を解析しない(個人名も団体名も受け付ける)
  - 1項目以上5項目以下の範囲で連名にすることもできる
- 住所・郵便番号を登録・編集・削除できる
- stage 1時点では郵便番号欄は手入力する(補完なし)

#### FR-1-3: 郵便番号から住所の順引き

- 郵便番号(7桁)を入力すると、郵便番号で一意に確定できる範囲で住所が自動補完される
- より具体的には、郵便番号を入力したフォームでenterキーを押すと、住所が補完される。郵便番号の入力中は補完しない。
- 補完後も住所は手動で編集できる

### Stage 2

### FR-2-1: 住所から郵便番号の逆引き

- ユーザが住所の一部を入力すると、該当する郵便番号と住所の組を表示する
- 候補が多すぎるときは何も表示しない。ユーザは入力を続けるはずなので、入力を妨げない。
- 候補が数件になったらクリックまたは上下カーソル(↑↓)キーで確定する
- 検索対象は、日本郵便が [提供する](https://www.post.japanpost.jp/zipcode/download.html) CSVファイルに準拠する
  - 住所の郵便番号 : 神奈川県横浜市中区日本大通から 231-0021 を得る
  - 事業所の個別郵便番号 : 神奈川県庁から 231-8588 を得る
- 事業所の個別郵便番号は、一般的な住所の郵便番号よりも先に表示する

### FR-2-2: インクリメンタル検索

- 住所の一部を入力するたびに候補が絞り込まれる
- 入力とは、キーストロークではなく、カナ漢字変換入力を一単位にする

## 3. 非機能要件 (NFR : Non-Functional Requirements)

### NFR-1: 応答時間

- 順引き（FR-1-3）：補完まで 3秒 以内（1回だけの操作のため許容範囲広め）
- 逆引きインクリメンタル検索（FR-2-1, FR-2-2）：入力から候補表示まで 100ms 以内。ユーザ入力に不自然な遅延を感じさせない応答速度にする。

### NFR-2: データソース

これらデータソースはアプリの運用に別途ダウンロードして組み込む。アプリに同梱して配布してはならない。

#### 郵便番号

日本郵便 `ken_all.csv`（UTF-8版）

- [ダウンロード元](https://www.post.japanpost.jp/zipcode/dl/utf-zip.html)
- 列名はCSVファイルに含まれないので、推測する

#### 大口事業所

日本郵便 `JIGYOSYO.CSV`

- [ダウンロード元](https://www.post.japanpost.jp/zipcode/dl/jigyosyo/index-zip.html)
- 列名はCSVファイルに含まれないので、推測する
- 元データはShift_JISであり、そのままでは扱えないのでUTF-8に変換する。Unicodeに変換不可能な文字が化けると、検索が不完全になる可能性があることは受け入れる。

### NFR-3: 検索仕様

- ワイルドカード（`*`）による部分一致を許可する
- 正規表現の直接入力は禁止（ReDOS対策）
- 入力が1文字以下の場合は検索しない（候補が多すぎるため）
- 日本語IMEの変換確定（compositionend）タイミングで検索を発火する

### NFR-4: 将来の拡張性

- 逆引き機能は、将来より賢いSaaSに置き換えられるよう、インターフェースをシンプルに保つ
- ブラウザ上で動くHTML+JavaScriptは、逆引きの実装詳細を知らなくてよい設計にする

---

## 4. スコープ外

- 住所の国際化（本サービスは日本国内に限定する）
- はがきに印刷する画像をアップロードして、どう印刷されるか編集する
- 課金
- 複数ユーザー対応・認証

---

## 5. データソースに関する既知の問題

ken_all.csv には以下の問題があり、テストで考慮が必要：

| 問題 | 具体例 | テストなしで起きること |
|------|--------|----------------------|
| 同一住所に複数郵便番号 | 大企業本社ビル | どれを返すか不定 |
| 町域名の分割レコード | 長い町名が2行に分割 | 結合しないと一致しない |
| 読み方の揺れ | 「ケ」「ヶ」「が」 | 検索漏れ |
| 地名の重複 | 「京橋」は東京・大阪・広島等に存在 | 複数都道府県が返る（仕様通りだが要確認） |
